##  دستورات پایه‌ی لینوکس چطور واقعاً کار می‌کنن ؟

### ⚙️ **Intro**

فصل اول کتاب معماری کلی سیستم رو نشون داد و فصل دوم یک قدم جلوتر میره و سراغ همون دستوراتی میره که هر روز باهاشون کار می‌کنیم. اما نه به‌عنوان یه لیست برای حفظ کردن، بلکه به‌ عنوان دریچه‌ ای برای دیدن اینکه کرنل واقعاً چطور کار می‌کنه.

---

### ⚙️ **What is Shell and how run command ?**

شل (مثل bash) صرفاً یه مفسر دستور نیست؛ یه محیط برنامه‌نویسی کوچیکه که به کاربر اجازه میده ابزارهای کوچیک رو کنار هم بچینه — دقیقاً همون فلسفه‌ی یونیکس که هر ابزار یه کار رو خوب انجام بده. بسیاری از دستورهایی که توی شل اجرا می‌کنیم با همین الگو پیش میرن: شل خط رو تحلیل می‌کنه، با فراخوانی system call ای به اسم fork()، یه process جدید می‌سازه، و بعد توی همون process تازه، تابع exec() رو صدا می‌زنه که برنامه‌ی فعلی رو با باینری موردنظر (مثلاً ls) جایگزین می‌کنه. البته همه‌ی دستورها این مسیر رو طی نمی‌کنن؛ built-in هایی مثل cd، export، یا alias مستقیم توسط خود شل اجرا میشن، بدون نیاز به fork جدا — و دلیلش رو توی بخش cd می‌بینیم.

📡 stdin/stdout؛ چرا cat بدون آرگومان منتظر می‌مونه؟
دستور cat یکی از ساده‌ترین ولی آموزنده‌ترین دستورهای یونیکسه. اسمش از concatenate (به‌هم‌چسبوندن) میاد و محتوای یک یا چند فایل رو چاپ می‌کنه. اما وقتی بدون هیچ آرگومانی اجراش می‌کنید، به‌جای خروجی فوری، منتظر ورودی می‌مونه — چون به‌جای خوندن از فایل، از standard input یا stdin می‌خونه؛ کانالی که Kernel برای هر process فراهم می‌کنه و در حالت عادی به همون ترمینال وصله. هر چی تایپ کنید رو دقیقاً تکرار می‌کنه، تا وقتی با Ctrl+D به سیستم اعلام کنید دیگه داده‌ای نیست (EOF).

هر process به همین ترتیب یه standard output یا stdout هم داره که خروجی معمولیش رو توش می‌نویسه، و یه جریان سوم به اسم standard error برای پیام‌های خطا. نکته‌ی کلیدی اینه که چون stdin/stdout فقط یه کانال هستن نه چیز ثابتی مثل «کیبورد» یا «مانیتور»، می‌شه مسیرشون رو عوض کرد — به یه فایل، یا به ورودی یه process دیگه. این دقیقاً همون مکانیزم زیربنایی pipe هاست (علامت |): خروجی یه برنامه مستقیم به ورودی برنامه‌ی بعدی وصل میشه، بدون این‌که خود دو برنامه اصلاً از وجود هم خبر داشته باشن.

🛠️ دستورهای فایل؛ نمونه‌هایی از همون منطق
▪️ ls اطلاعات یه دایرکتوری رو از Kernel درخواست می‌کنه؛ با گزینه‌ی ls -l مالک، گروه، حجم، و زمان آخرین تغییر فایل‌ها رو هم می‌بینید.
▪️ cp نشون میده کپی کردن در سطح پایین چیزی نیست جز خوندن یه فایل و نوشتنش توی فایل دیگه.
▪️ mv معمولاً خیلی سریع‌تر از cp عمل می‌کنه؛ چون اگه مبدا و مقصد روی یه درایو باشن، فقط یه ورودی توی جدول دایرکتوری جابه‌جا میشه، نه خود داده روی دیسک — یعنی فقط metadata عوض میشه.
▪️ touch یه فایل خالی می‌سازه؛ اگه فایل از قبل باشه، فقط زمان آخرین تغییرش آپدیت میشه، محتواش دست نمی‌خوره.
▪️ rm یه درخواست حذف یه ورودی از دایرکتوریه — و چون معمولاً سطل بازیافتی در کار نیست، باید باهاش محتاط بود. نکته‌ی امنیتی جالب اینه که حذف یه فایل در لینوکس معمولاً به معنی پاک شدن فوری داده‌ها از دیسک نیست؛ فقط ارتباط اون فایل با اسمش توی filesystem قطع میشه، و تا وقتی داده‌های فیزیکی روی دیسک بازنویسی نشده باشن، ممکنه هنوز قابل بازیابی باشن.
▪️ echo آرگومان‌هاش رو مستقیم روی stdout چاپ می‌کنه؛ برای دیدن نتیجه‌ی متغیرها و الگوهای شل خیلی کاربردیه.

🗂️ مسیرها و منطق پیمایش
ساختار دایرکتوری‌های یونیکس از / (ریشه یا root directory) شروع میشه. مسیری که با / شروع بشه، absolute path ـه؛ در غیر این صورت relative path. دو نماد کلیدی هم هست: . (همین دایرکتوری) و .. (دایرکتوری والد).

cd دایرکتوری فعلی شل رو عوض می‌کنه؛ بدون آرگومان، به home directory (که با ~ هم نشون داده میشه) برمی‌گرده. نکته‌ی فنی جالب: cd باید حتماً یه دستور داخلی خود شل باشه، نه یه برنامه‌ی مستقل. چرا؟ چون هر process یه وضعیت داخلی به اسم «دایرکتوری کاری فعلی» داره که Kernel نگه‌داریش می‌کنه. اگه cd یه برنامه‌ی جدا بود، طبق همون چرخه‌ی fork+exec، تغییر دایرکتوری توی یه process فرزند جدا اتفاق می‌افتاد، نه توی خود شل — و به محض تموم شدن اون process، تغییر هم از بین می‌رفت. برای همینه که cd باید built-in باشه.

mkdir و rmdir به ترتیب یه دایرکتوری جدید می‌سازن یا یه دایرکتوری خالی رو حذف می‌کنن. rmdir فقط روی دایرکتوری خالی کار می‌کنه؛ برای حذف کامل یه دایرکتوری همراه با محتویاتش، باید از rm -r استفاده کرد — دستوری که مخصوصاً با دسترسی root باید با احتیاط زیاد اجرا بشه.

✨ Globbing؛ یکی از نکات طلایی این فصل
شل می‌تونه الگوهای ساده رو با اسم فایل‌ها تطبیق بده. ستاره (*) هر تعداد کاراکتر دلخواه رو نشون میده و علامت سؤال (?) دقیقاً یه کاراکتر رو.

نکته‌ی مهمی که خیلیا نمی‌دونن اینه: وقتی می‌نویسید ls *.log، این خود دستور ls نیست که داره دنبال فایل‌ها می‌گرده. این شله که قبل از اجرای دستور، الگوی *.log رو با اسم واقعی فایل‌های موجود توی همون دایرکتوری جایگزین می‌کنه. یعنی اگه توی پوشه سه‌تا فایل به اسم app.log، error.log، و access.log داشته باشید، دستوری که واقعاً اجرا میشه چیزیه شبیه ls app.log error.log access.log — و ls اصلاً نمی‌فهمه که یه الگو در کار بوده.

همین یه نکته کافیه که بفهمیم چرا برنامه‌ها توی یونیکس ساده‌تر طراحی میشن؛ چون لازم نیست هر برنامه خودش منطق پیدا کردن فایل‌ها رو پیاده‌سازی کنه — این کار یه‌بار برای همیشه توی شل انجام شده.

💡 جمع‌بندی
نکته‌ی محوری این فصل اینه که دستورات پایه‌ی یونیکس صرفاً یه رابط کاربری روی یه مجموعه محدود از system call ها هستن. وقتی این لایه‌ی زیرین رو بشناسید، خیلی از رفتارهای به‌ظاهر عجیب (چرا mv بین دو دیسک کند میشه؟ چرا cat بدون آرگومان منتظر می‌مونه؟ چرا cd باید built-in باشه؟) دیگه عجیب نیستن — نتیجه‌ی مستقیم طراحی Kernel هستن.
